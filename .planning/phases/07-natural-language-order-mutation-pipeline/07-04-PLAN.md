<objective>
Close UAT Gap 2 with a permanent, generalized order matching architecture:
1. Eliminate substring false-positive matching: Register a native SQLite `word_match` function with word boundary logic (`\\b{token}\\b`) so searching for short names ("Hà", "An", "Ba", "Lê") never matches substrings ("Thanh", "Thảo", "Khánh", "Hoàng").
2. Support arbitrary multi-field composite search: Enable matching across any combination of customer name, phone, shipping address (ward, district, city), items text, and notes (e.g. "anh Tuấn Gia Lâm", "Bác Ba Cần Thơ", "đơn 3 cuốn Chế Linh").
3. Unify with Phase 4 Text-to-SQL search engine: When local multi-token word matching finds 0 results for complex natural language queries, delegate to `execute_natural_language_search` filtered for active orders.

Purpose: Ensure users can identify orders for mutation using any arbitrary natural phrasing without hardcoded cases or substring errors.
Output: Generalized matching in `src/db/connection.py`, `src/db/orders.py`, `src/bot/handlers/mutation.py`, and regression suite in `tests/test_mutation_search_general.py`.
</objective>

    - Test 2: `find_orders_for_mutation` with keyword "anh hà" finds only order with customer_name="Hà", completely ignoring customer named "Thanh".
    - Test 3: `find_orders_for_mutation` with multi-field tokens "tuấn gia lâm" matches an order where customer_name="Tuấn" and shipping_address="123 Gia Lâm, Hà Nội".
    - Test 4: `find_orders_for_mutation` matches items_text (e.g. "Chế Linh") and shipping_address (e.g. "Đà Nẵng") when query is "đơn Chế Linh Đà Nẵng".
    - Test 5: Searches prioritize active orders (`CHO_LAM` .. `SHIPPER_DA_LAY`) over completed ones (`DA_GIAO`, `BOM_HANG`, `HUY_DON`).
  </behavior>
  <action>
    1. In `src/db/connection.py`:
       - Define Python helper `sqlite_word_match(haystack: str | None, needle: str | None) -> int`:
         Return 0 if either is None or empty.
         Normalize both using `remove_accents`.
         Use regex `re.search(rf"\b{re.escape(needle_clean)}\b", haystack_clean)` returning 1 if match else 0.
       - In `get_db_connection`, register `await db.create_function("word_match", 2, sqlite_word_match)`.
    2. In `src/db/orders.py`:
       - Refactor `find_orders_for_mutation` to perform generalized multi-field matching:
         Instead of checking only `unaccent(customer_name) LIKE ? OR customer_phone LIKE ?`:
         Construct combined searchable expression:
         `unaccent(customer_name || ' ' || customer_phone || ' ' || shipping_address || ' ' || items_text || ' ' || COALESCE(notes, ''))`
         - Tokenize cleaned keyword after stripping prefix fillers (`khach`, `don`, `cua`, `cho`, `giao`).
         - Strip honorifics (`anh`, `chi`, `bac`, `ong`, `ba`, `chu`, `co`, `em`) ONLY when building core tokens, but keep distinct substantive tokens.
         - For each substantive token $T$: require `word_match(searchable_text, ?) = 1` OR `searchable_text LIKE ?` (for partial code/phone matches).
         - Combine token conditions with `AND`: every substantive token in user query must match within the order's composite data.
         - Keep active status prioritization (`ACTIVE_MUTATION_STATUSES` first, backfill `TERMINAL_MUTATION_STATUSES` up to limit).
    3. Create `tests/test_mutation_search_general.py`:
       - Verify word boundary matching isolates short names.
       - Verify composite search works across (name + address), (name + items), (phone + address).
  </action>
